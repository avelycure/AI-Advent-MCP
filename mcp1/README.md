# Дни 16–19. MCP, GitHub API, планировщик и композиция инструментов

Это единый учебный проект для четырёх последовательных заданий:

- MCP-сервер на `http://127.0.0.1:3000/mcp`;
- MCP-клиент, который получает список инструментов через `listTools()` и
  вызывает выбранный инструмент через `callTool()`;
- простой инструмент `hello` из дня 16;
- read-only инструмент `github_repository_stats` из дня 17;
- персистентный планировщик GitHub-статистики из дня 18;
- автоматический пайплайн `search` → `summarize` → `save_to_file` из дня 19.

GitHub-инструмент обходит через REST API все репозитории, доступные токену, и
возвращает агрегированную статистику: количество репозиториев, звёзды, форки,
открытые issue/PR, основные языки и небольшой top-N.

## Установка и токен

Требуется Node.js 20.3 или новее.

```bash
cd mcp1
npm install
cp ../secrets/keys.example ../secrets/.env
chmod 600 ../secrets/.env
```

Впишите токен в `../secrets/.env`:

```dotenv
GITHUB_TOKEN=github_pat_...
```

Файл `secrets/.env` исключён из Git.

## Раздельный запуск сервера и клиента

В первом терминале:

```bash
cd mcp1
npm run server
```

Сервер продолжит работать и выведет:

```text
MCP server listening on http://127.0.0.1:3000/mcp
```

Во втором терминале:

```bash
cd mcp1
npm run client -- --list
```

В поле `tools` должны быть восемь инструментов:

- `hello`;
- `github_repository_stats`;
- `github_stats_schedule_upsert`;
- `github_stats_summary`;
- `search`;
- `summarize`;
- `save_to_file`;
- `search_summary_pipeline`.

Вызов GitHub-инструмента:

```bash
npm run client -- \
  --tool github_repository_stats \
  --arguments '{"visibility":"all","top":3}'
```

Команда `npm start` запускает клиент. Сервер должен быть уже запущен отдельной
командой `npm run server`.

## Входные параметры GitHub-инструмента

- `visibility`: `all`, `public` или `private`;
- `affiliations`: `owner`, `collaborator`, `organization_member`;
- `includeForks`: учитывать форки;
- `includeArchived`: учитывать архивные репозитории;
- `top`: размер списка лидеров, от 1 до 20.

Важно: при `visibility: "all"` агрегаты приватных репозиториев и обезличенные
строки top-N попадут в ответ инструмента. Если агент использует внешнюю LLM, эти
данные будут отправлены её провайдеру. Для анализа только открытых данных
задайте `visibility: "public"`.

## Периодический сбор: Day 18

Создать задачу `work` или обновить её с тем же `taskId`:

```bash
npm run client -- \
  --tool github_stats_schedule_upsert \
  --arguments '{"taskId":"work","intervalMinutes":15,"visibility":"public","top":5}'
```

По умолчанию первый сбор выполняется сразу, а следующие — в фоне через указанный
интервал. Минимальный production-интервал — 5 минут, максимальный — 7 дней.
Первый запуск можно отложить параметром `"runImmediately": false`, а расписание
приостановить параметром `"enabled": false`.

Получить последний успешный результат, историю и разницу с предыдущим успешным
сбором:

```bash
npm run client -- \
  --tool github_stats_summary \
  --arguments '{"taskId":"work","historyLimit":10}'
```

`delta` содержит числовые изменения в `repositories`, `totals` и `languages`.
До второго успешного запуска `delta` равен `null`. Ошибочные запуски остаются в
`history`, но не заменяют `latest` и не участвуют в сравнении.

Состояние хранится в `mcp1/data/github-stats-scheduler.json`, каталог исключён
из Git, а сам JSON создаётся с правами `0600`. Токен GitHub туда не записывается.
Путь можно переопределить переменной `MCP_STATE_FILE`. Хранятся последние 50
запусков каждой задачи; `historyLimit` ограничивает только размер ответа. Чтобы
случайно не размножить фоновые обращения к GitHub, одновременно поддерживаются
не более 20 задач.

Планировщик рассчитан на один процесс MCP-сервера. Несколько процессов не должны
использовать один state-файл одновременно: межпроцессной блокировки в учебной
реализации нет. Запись выполняется атомарной заменой файла. Повреждённый или
неподдерживаемый JSON не перезаписывается — сервер завершает запуск с ошибкой,
чтобы не потерять историю незаметно. При `SIGINT`/`SIGTERM` активный GitHub-запрос
отменяется, завершённое состояние сохраняется перед остановкой.

## Композиция инструментов: Day 19

Три самостоятельных MCP-инструмента образуют цепочку:

1. `search` получает компактные данные о публичных репозиториях через GitHub
   Search API. Сервер автоматически добавляет к запросу `is:public`, не отправляет
   GitHub-токен в search-запросе и отбрасывает элементы с признаком `private`.
2. `summarize` принимает весь `structuredContent` первого инструмента и строит
   детерминированный Markdown без обращения к внешней LLM.
3. `save_to_file` атомарно сохраняет результат в `mcp1/reports/`.

Инструмент `search_summary_pipeline` автоматически выполняет все три стадии
одним вызовом. В его ответе поле `stages` показывает порядок и метаданные передачи,
а поля `search`, `summary` и `saved` содержат результаты каждой стадии. Если стадия
завершилась ошибкой, последующие стадии не запускаются.

Чтобы увидеть передачу данных непосредственно в терминале MCP-сервера, передайте
`"trace": true`. Сервер напечатает вход каждого этапа, включая полный
`searchResult`, который получает `summarize`, и Markdown, который получает
`save_to_file`. В текущем примере `summarize` — детерминированный обработчик без
внешней LLM, поэтому trace показывает именно межинструментную передачу данных.

Каталог можно переопределить переменной `MCP_OUTPUT_DIR`, но клиент не может
выбрать произвольный путь. Имя файла должно быть простым basename с расширением
`.md` или `.txt`; абсолютные пути, вложенные каталоги и path traversal отклоняются.
Новый каталог создаётся с правами `0700` (права существующего `MCP_OUTPUT_DIR`
не меняются), файл — с `0600`; запись выполняется через временный файл. По умолчанию
существующий отчёт не перезаписывается; для повторяемого демо передайте
`"overwrite": true`.

### Какую задачу выполняет команда

Мы хотим одной MCP-командой решить прикладную задачу: найти публичные GitHub-
репозитории по теме `model context protocol`, превратить результаты поиска в
короткий Markdown-отчёт и сохранить его в файл.

Команда во втором терминале:

```bash
cd mcp1
npm run pipeline -- \
  "найти 3 публичных GitHub-репозитория по теме model context protocol, сделать Markdown-отчёт и сохранить его в файл"
```

CLI разбирает эту фразу и получает параметры пайплайна:

- `query = "model context protocol"` — тема после слов «по теме»;
- `limit = 3` — число после слова «найти»;
- `fileName = "model-context-protocol-report.md"` — безопасное имя по теме;
- `overwrite = true` — повторный запуск обновляет тот же отчёт;
- `trace = true` — сервер показывает фактический вход каждой стадии.

После разбора CLI вызывает MCP-инструмент `search_summary_pipeline`. В клиентском
терминале будут видны распознанная задача, запущенный инструмент, пройденные стадии
и итоговый файл. В серверном терминале будут видны полные передаваемые объекты.

### Что происходит под капотом

Сначала CLI превращает русскую команду в JSON и MCP-клиент отправляет серверу один
вызов `search_summary_pipeline`. Дальше сервер последовательно выполняет три
операции.

#### 1. `search` получает исходные данные

На вход операции попадает часть аргументов команды:

```json
{
  "query": "model context protocol",
  "limit": 3
}
```

`search` обращается к публичному GitHub Search API и возвращает
`structuredContent`. Сокращённый пример результата:

```json
{
  "query": "model context protocol",
  "totalCount": 1200,
  "items": [
    {
      "fullName": "example/mcp-server",
      "description": "Example MCP server",
      "url": "https://github.com/example/mcp-server",
      "language": "JavaScript",
      "stars": 42,
      "forks": 7
    }
  ]
}
```

Это результат первого инструмента и одновременно данные для второго. Pipeline не
берёт их из файла и не просит пользователя копировать JSON вручную.

#### 2. Результат `search` передаётся в `summarize`

Pipeline берёт весь объект `search.structuredContent` и формирует следующий вход:

```json
{
  "searchResult": {
    "query": "model context protocol",
    "totalCount": 1200,
    "items": ["полные элементы из результата search"]
  }
}
```

`summarize` преобразует эти структурированные данные в Markdown и возвращает:

```json
{
  "query": "model context protocol",
  "itemCount": 3,
  "summary": "# GitHub search: model context protocol\n\nFound ..."
}
```

#### 3. Markdown передаётся в `save_to_file`

Pipeline берёт ровно поле `summarize.structuredContent.summary` и передаёт его
третьей операции:

```json
{
  "fileName": "model-context-protocol-report.md",
  "content": "# GitHub search: model context protocol\n\nFound ...",
  "overwrite": true
}
```

`save_to_file` атомарно записывает текст и возвращает метаданные результата:

```json
{
  "fileName": "model-context-protocol-report.md",
  "bytes": 640,
  "savedAt": "2026-09-28T10:00:00.000Z"
}
```

Итоговый поток выглядит так:

```text
аргументы команды
  → search
  → search.structuredContent
  → summarize({ searchResult })
  → summarize.structuredContent.summary
  → save_to_file({ content })
  → reports/model-context-protocol-report.md
```

Фактические значения конкретного запуска будут видны в первом терминале в блоках
`INPUT -> search`, `INPUT -> summarize` и `INPUT -> save_to_file`. Итоговый файл:

```bash
sed -n '1,160p' reports/model-context-protocol-report.md
```

Важно: внешняя LLM в этой реализации не вызывается. `summarize` — обычная
детерминированная функция, поэтому данные передаются между MCP-операциями внутри
сервера. В реальном агентском клиенте модель могла бы сама выбрать и вызвать три
отдельных инструмента; здесь автоматическую оркестрацию выполняет
`search_summary_pipeline`.

## Проверка

```bash
npm test
```

Тесты запускают настоящий MCP client/server transport, проверяют восемь
инструментов, пагинацию GitHub, защиту токена, фоновый запуск, отсутствие overlap,
retention состояния после рестарта, расчёт delta, точную передачу данных между
стадиями пайплайна, остановку после ошибки и безопасную запись файлов. GitHub API
в тестах подменён, поэтому сеть и настоящий токен не нужны.
