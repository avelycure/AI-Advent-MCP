# День 20. Orchestration MCP

Демонстрационный проект регистрирует два независимых MCP-сервера, обнаруживает
их инструменты через `listTools()` и выполняет длинный сценарий без ручной
передачи данных между шагами.

Это детерминированный orchestration agent без внешней LLM. Он выбирает инструмент
по его имени, описанию и полям входной схемы, поэтому выбор можно повторить и
точно проверить тестом.

## Серверы и инструменты

Серверы явно зарегистрированы в `config/servers.json`:

| MCP-сервер | Инструменты | Назначение |
| --- | --- | --- |
| `catalog` (`mcp2`) | `search_learning_resources`, `get_resource_details` | поиск и раскрытие учебных ресурсов |
| `planning` (`mcp3`) | `rank_learning_resources`, `create_learning_plan`, `save_learning_plan` | ранжирование, построение и сохранение плана |

У каждого инструмента есть Zod/JSON Schema, описание и MCP-аннотации. Имена
инструментов должны быть уникальны между серверами: неоднозначная регистрация
останавливается до выполнения пользовательского запроса.

## Как агент строит маршрут

Агент получает список всех инструментов обоих серверов. Для каждой требуемой
способности он сопоставляет смысловые маркеры с `name`/`title`/`description` и
проверяет необходимые поля `inputSchema`. Побеждает единственный инструмент с
максимальной оценкой; отсутствие инструмента или ничья считаются ошибкой.
Поисковый сервер передаёт `relevanceScore` и совпавшие термины серверу
планирования, поэтому последующее ранжирование не теряет релевантность поиска.

Для полного запроса строится такой логический маршрут:

```text
catalog.search_learning_resources
  → planning.rank_learning_resources
  → catalog.get_resource_details × выбранные ресурсы
  → planning.create_learning_plan
  → planning.save_learning_plan
```

Таким образом, поток действительно меняет сервер: `catalog → planning → catalog
→ planning`. Каждый следующий шаг получает `structuredContent` предыдущего.
При ошибке или пустом поиске последующие инструменты не вызываются.

## Запуск

Требуется Node.js 20.3 или новее. Один раз установить зависимости:

```bash
cd mcp2 && npm install
cd ../mcp3 && npm install
```

Терминал 1 — сервер каталога:

```bash
cd mcp2
npm run server
```

Терминал 2 — сервер планирования:

```bash
cd mcp3
npm run server
```

Терминал 3 — интерактивный запрос агенту:

```bash
cd mcp3
npm run orchestrate
```

Программа покажет приглашение. Теперь запрос вводите вы сами прямо в терминале:

```text
Введите текстовую команду для агента и нажмите Enter:
> Подбери 3 учебных ресурса по теме MCP, ранжируй их, изучи детали каждого, составь практический план обучения и сохрани его в day-20-mcp-plan.md
```

Встроенного демо-запроса нет. Пустая команда не выполняется. Обычный запрос не
перезаписывает существующий файл: для этого после имени файла нужно явно добавить
«и при наличии перезапиши файл» или `and overwrite`.

Для автоматизации запрос всё ещё можно передать аргументом. Чистый JSON выводится
так:

```bash
npm run --silent orchestrate -- --json \
  "Подбери 2 ресурса по теме MCP, составь план и сохрани его в result.md"
```

URL можно переопределить переменными
`MCP_CATALOG_URL` и `MCP_PLANNING_URL`, а каталог результата —
`MCP_PLAN_OUTPUT_DIR` у planning-сервера.

Учебный HTTP-режим намеренно принимает только точные URL вида
`http://127.0.0.1:<port>/mcp`, не следует редиректам и ограничивает ответ 1 МБ.
Серверы рассчитаны на запуск от обычного пользователя в одном локальном проекте,
а не как привилегированный или публичный сервис. Planning-сервер не является
границей безопасности между процессами одного локального пользователя; для
production-развёртывания нужен аутентифицированный transport.

## Наглядный результат

CLI сначала показывает исходный текст и обнаруженные инструменты:

```text
ЗАПРОС ПОЛЬЗОВАТЕЛЯ:
Подбери 3 учебных ресурса по теме MCP, ранжируй их, изучи детали каждого,
составь практический план обучения и сохрани его в day-20-mcp-plan.md

ЗАРЕГИСТРИРОВАННЫЕ MCP-СЕРВЕРЫ:
- catalog: search_learning_resources, get_resource_details
- planning: rank_learning_resources, create_learning_plan, save_learning_plan
```

Затем видны выбор и фактический порядок вызовов:

```text
ШАГ 1: catalog.search_learning_resources
  вход:  { topic: "MCP", maxResults: 5 }
  выход: 4 кандидата

ШАГ 2: planning.rank_learning_resources
  вход:  4 кандидата, desiredCount: 3
  выход: mcp-architecture, mcp-security, mcp-tools

ШАГ 3: catalog.get_resource_details
  вход:  mcp-architecture
  выход: 45 минут, 3 учебных модуля

ШАГ 4: catalog.get_resource_details
  вход:  mcp-security
  выход: 55 минут, 3 учебных модуля

ШАГ 5: catalog.get_resource_details
  вход:  mcp-tools
  выход: 60 минут, 3 учебных модуля

ШАГ 6: planning.create_learning_plan
  вход:  полные объекты трёх ресурсов
  выход: Markdown-план на 160 минут

ШАГ 7: planning.save_learning_plan
  вход:  имя файла и точный Markdown шага 6
  выход: mcp3/output/day-20-mcp-plan.md, 1902 байта
```

Финальная часть вывода:

```text
ИТОГ:
Файл: .../mcp3/output/day-20-mcp-plan.md
Ресурсы: mcp-architecture, mcp-security, mcp-tools
Общее время: 160 минут
```

## Проверки

```bash
cd mcp2 && npm test
cd ../mcp3 && npm test
```

Тесты проверяют discovery обоих серверов, выбор инструментов, маршрут из семи
вызовов, точные handoff-объекты, пустой результат, посторонний запрос, конфликт
имён, безопасную запись и реальный HTTP-флоу между двумя отдельными процессами.
